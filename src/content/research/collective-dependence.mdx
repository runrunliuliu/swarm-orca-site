## 单个无害，集体却可能失准

在多 Agent 系统的安全与工程讨论中，我们习惯先检查单个模型是否对齐、单条消息是否越界。但如果把视角放大到整个协作过程，一个更隐蔽的问题会出现：**每一个 Agent 的单步输出看起来都合理，合在一起却可能触发越界行为或偏离原本的目标。**

Artificial Societies 发布的 **Collective Dependence Analysis（CDA）** 把这类现象称为“集体失准（collective misalignment）”。在多 Agent 对话与协作中，某些信息在单条消息层面并不构成违规，但当它们跨角色拼接、累积并被后续执行者采纳时，整体轨迹就可能越过安全或业务边界。传统做法往往只盯着单个节点做审核，很难回答一个关键问题：究竟是哪几条交互消息、哪一段依赖关系，共同促成了最终的异常结果？[研究原文](https://societies.ai/collective-dependence)

CDA 的核心思路，是把因果归因中的 **必要性（necessity）** 与 **充分性（sufficiency）** 引入多 Agent 交互记录的分析中：它区分解释异常结果的消息集合，以及在已测试候选中能够阻断违规结果的最小移除集合。在作者报告的 485 个 Agent 自由交互违规案例中，移除 CDA 选出的消息后，违规率从 98% 降至 9%，正常任务的成功率从 20% 升至 79%。这些数字来自该研究的特定实验设置，不能直接外推为其他系统的普遍效果。[Collective Dependence Analysis](https://societies.ai/collective-dependence)

这对工程实践的启发很直接：多 Agent 协作的风险，不只是“某个 Agent 犯了错”，更在于**信息在交接过程中如何被放大、重组并变成后续动作的依据**。

## 这对 Swarm-Orca 意味着什么：我们可以做的事

Swarm-Orca 并不是一个专门做安全归因研究的评测框架，但 CDA 揭示的“跨消息依赖导致集体偏航”问题，恰好对应了工程协作中反复出现的痛点。结合 Swarm-Orca 围绕任务上下文、角色分工和可验证交付的设计方向，工程侧可以推进几件具体的事：

1. **把隐式对话变成显式的任务边界与交接契约**
   很多集体跑偏，源于上下文在多轮聊天中被不断改写或默认继承。Swarm-Orca 可以在任务启动与交接时固定目标、代码基线、允许修改的范围与停止条件，让后续执行者依据明确的边界工作，而不是仅凭前序消息的只言片语继续推理。

2. **在关键依赖节点设置独立审查与人工闸门**
   CDA 说明并非所有消息都同等重要，真正决定轨迹走向的往往是少数关键交接。对应到 Swarm-Orca 的角色分工，协调、实施与独立审查分开后，审查者不必重读所有闲聊，而是重点核对高影响变更、外部副作用操作与跨模块接口变化，在合并或执行前打断不合理的依赖链。

3. **保留可追溯的因果记录，而不只存最终结果**
   如果只保存“任务成功或失败”的标签，事后很难判断是哪一步交接引入了错误前提。Swarm-Orca 可以通过结构化的交付记录，把产物、测试命令、代码版本与“结果未知”的不确定状态关联起来，为后续回溯哪一步依赖导致偏航提供可检查的日志基础。

4. **探索面向工程轨迹的轻量依赖检查**
   基于公开的任务与交接记录，未来可以进一步验证：能否借鉴 CDA 的必要性与充分性思路，在多 Agent 工程任务中识别“哪几条交接信息改变了最终实现路径”，从而更早发现冗余沟通、基线漂移或潜在的越界指令组合。这仍属于待验证的研究与工程方向，需要通过具体任务和对照测试来检验效果与成本。

因此，本文把 CDA 作为一种观察协作依赖的研究视角：不假设单个 Agent 永远可靠，而是关注信息如何跨角色传播、哪些交接会改变后续行为，以及工程边界能否让这种影响更容易被检查。把这一视角落到 Swarm-Orca 仍需要实现与对照实验，不能由设计讨论直接推导出安全效果。
