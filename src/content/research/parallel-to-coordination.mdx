## 从并行到协作

让多个 Agent 同时工作，正在成为处理复杂任务的一种自然选择：一个分析问题，一个编写代码，另一个负责审查。但当任务持续数小时、横跨多个模块，而且每一步都依赖此前的结果时，“同时工作”并不等于“共同推进”。谁负责哪个部分？接口变化后谁需要调整？某个 Agent 宣布完成，是否意味着整个任务已经通过验收？

Bespoke Labs 发布的 **Multi Agent Coordination Bench（MAC Bench）**，把这一区别变成了可测量的问题。它包含十二项长时程任务，通过单 Agent、多 Agent 协作，以及无协作对照，区分“增加执行者带来的收益”和“协调本身带来的收益”。在其测试设置下，八 Agent 团队的平均得分高于单 Agent，却没有超过无协作对照；整体协调增益未达到统计显著。这并不证明协作无用，而是提醒我们：团队表现的提升，不能仅凭 Agent 数量来解释。[研究原文](https://benchmarks.bespokelabs.ai/multi-agent-coordination-bench/)

这里还有一个重要的实验细节：无协作对照并不总是“关闭群聊”。对于多数共享型任务，它采用多个独立 Agent 分别求解、再取最好结果的方式。因此，这项研究提出的挑战更具体：**组织一个团队，能否比让同样数量的 Agent 独立探索更有价值？** 这一比较固定的是运行时长，而不是总费用；不能把它直接理解为等成本条件下的优劣。[实验设置与协调增益定义](https://benchmarks.bespokelabs.ai/multi-agent-coordination-bench/)

这也是 Swarm-Orca 试图从工程侧回答的问题。我们的出发点，是把协作中的约定变成可以检查的任务与执行记录：开始前明确目标、工作范围和验收标准；执行中区分协调、实施与独立审查的职责；交接时保留代码基线、产物和测试证据。消息已经送达、Agent 已经结束一轮回答，与任务真正完成，是不同的事实。

这些设计并不能直接证明 Swarm-Orca 已经解决了协调问题。它们首先提供了一种分析问题的基础：出现重复劳动时，可以检查任务归属；上下游无法衔接时，可以追溯接口与版本；执行中断时，可以核对已发生的动作，而不是从头猜测。至于这些机制能否改善完成质量、缩短耗时，并抵消额外的沟通与审查成本，仍需要对照实验来验证。

因此，这篇文章将从 MAC Bench 对“协调收益”的拆分出发，介绍 Swarm-Orca 的设计取舍。我们关心的不只是能启动多少个 Agent，而是：**在什么任务、什么组织方式和什么成本下，多个 Agent 才值得一起工作？**

## 为什么“多开几个 Agent”不一定更好

在评估多 Agent 系统时，一个常见的误区是把“团队击败了单 Agent”直接等同于“协作产生了价值”。MAC Bench 的对照思路提醒我们，多 Agent 至少包含两种不同来源的收益：一种是**并行探索收益**，即更多执行者带来更多的尝试路径和更大的覆盖面；另一种才是**协调收益**，即成员之间通过分工、共享中间发现与互相修正，取得了独立尝试难以达到的结果。

如果任务本身高度可分、子问题之间几乎没有耦合，或者最终只需要从多次独立尝试中挑选最佳解，那么无协作的并行往往已经足够，甚至更稳妥。因为一旦引入实时协调，系统就会立刻承担额外的工程成本：

- **上下文同步成本**：每个成员都需要理解最新目标、代码基线与他人已经做出的改动，信息传递稍有遗漏就会产生基线漂移。
- **职责模糊与重复劳动**：如果没有明确的任务归属和文件边界，多个 Agent 很容易同时修改同一处逻辑，或在交接缝隙中漏掉关键步骤。
- **过早收口的风险**：当一个 Agent 在局部视角下报告“已完成”时，如果没有独立核查，协调者很难判断它是否真的满足全局约束，还是只完成了局部自述。

换句话说，协调不是免费的增强器。只有当任务存在跨模块依赖、阶段性状态耦合，或者需要持续分工与集成验证时，协调机制才可能带来净收益；否则，沟通与等待的开销很容易抵消并行本身的优势。

## Swarm-Orca 的三个设计取舍

围绕“让协调过程可检查、可追溯”这一目标，Swarm-Orca 在工程设计上做了三项核心取舍。它们对应的是协作中最容易失控的三个环节：任务上下文、角色边界与交付判断。

### 1. 围绕任务组织上下文与工作区

在多 Agent 场景里，“把问题修好”这样的提示词只表达了意图，没有给出工作条件。Swarm-Orca 倾向于把任务作为一等边界来组织信息，在启动执行前尽量明确四件事：目标是什么、代码基线是什么、允许修改什么范围，以及通过什么方式验收。

在此基础上，独立工作区的作用不只是避免并行编辑时的文件冲突，更在于把代码变更、运行产物与测试证据绑定到同一条任务工作线上。当后续需要修正、恢复或继续推进时，执行者可以沿用既有上下文，而不是每次从一段新的对话重新开始。

### 2. 把协调、实施与审查分开

为了减少“自己写、自己测、自己宣布通过”带来的盲区，Swarm-Orca 将协作中的职责划分为协调、实施与独立审查三个关注点：

| 角色关注点 | 核心职责 | 需要明确回答的问题 |
| --- | --- | --- |
| 协调 | 拆解目标、管理依赖与推进节奏 | 当前先推进哪一步，什么情况下应当停止或调整？ |
| 实施 | 在约定范围内修改代码并自检 | 改了哪些文件，跑了什么验证，还有哪些已知限制？ |
| 审查 | 对照需求与证据独立核查 | 产物是否完整，测试是否覆盖当前版本与关键风险？ |

这种分工的价值并不来自角色名称本身，而来自清晰的责任边界。当然，角色拆分也会增加交接轮次与等待时间，因此它更适合改动面较大、错误代价较高的任务，而不是所有简单任务都套用同一套重流程。

### 3. 把“完成反馈”与“可验证交付”分开

在多数对话式 Agent 工作流中，“回复结束”常常被默认当成“任务完成”。但在长时程协作里，消息送达、轮次结束与真正满足验收条件之间存在明显落差。

Swarm-Orca 的做法是要求交接保留最小限度的结构化事实：变更对应哪一个基线、实际执行了哪些检查命令、输出了什么结果，以及有哪些场景尚未覆盖。同时，对于超时、中断或外部状态未确认的情况，记录应明确标出“结果未知”，避免在事实不清时盲目重试或误判成功。

> 上游能力与项目边界：Swarm-Orca 的通用协作工具与其依赖的上游 Orca 各有分工。后续文章会进一步区分上游已有能力、项目新增编排机制与仍在演进中的设计，不将讨论中的方案写成既定能力。

## 哪些任务值得协作，以及如何验证

回到文章开头的问题：在什么任务、什么组织方式和什么成本下，多个 Agent 才值得一起工作？从当前的工程观察出发，我们更倾向于把协作视为一种**按任务复杂度按需启用的结构**，而不是默认选项：

1. **先判断耦合度**：如果子任务彼此独立且只需择优，优先考虑无协作并行；只有当子任务共享状态、接口相互约束或需要多阶段集成时，才引入角色分工与交接机制。
2. **明确收益与成本的账本**：评估协作是否有效，不能只看单次任务的最高得分，还需要同时记录完成质量、端到端耗时、沟通与审查带来的额外开销，以及失败后的恢复成本。
3. **用对照实验替代直觉**：参考 MAC Bench 的拆分思路，后续验证 Swarm-Orca 的机制时，应在同一批可复现任务上对比单 Agent、无协作并行与结构化协作的表现，明确任务类型、样本范围与限制条件。
