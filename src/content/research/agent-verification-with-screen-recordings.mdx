## 代码通过测试，为什么还不算完成

Agent 很擅长交付一组看起来完整的结果：改动已经写入，类型检查通过，单元测试也是绿色。对于纯函数或边界明确的后端逻辑，这些证据往往已经很有说服力；但只要功能跨越了 UI、进程、机器或运行环境，“代码正确”与“用户真的能用”之间仍隔着一段距离。

[Swarm-Orca Issue #67](https://github.com/runrunliuliu/swarm-orca/issues/67) 就是一个典型案例。任务页需要展示某个 Issue 对应的历史 Agent 运行记录。在本机有记录时，一切正常；但当记录只存在于已配对的远端环境，本地客户端会显示：没有工作区、没有 Agent、这项任务从未运行过。

远端并不是没有数据。真正的问题是，客户端选择查询环境时只使用了本地已有的工作区和绑定信息。远端记录本可证明“我属于哪个环境”，客户端却必须先知道环境，才会去读取这条记录。这个循环依赖导致远端请求根本没有发出。单独测试记录读取、合并或 UI 组件，都可能通过；只有沿着真实入口跑一遍，问题才会暴露。

因此，这次修复的验收问题不能只写成“相关测试通过”，而应该写成一条用户可观察的陈述：**在本地没有该任务记录、记录只存在于已配对远端的前提下，打开任务页，能够看到远端归档工作区和历史 Agent；无法确认的用量仍然显示为未知。**

## 录屏验证的，不只是最终画面

截图可以证明某个时刻出现过一个界面，录屏则可以把前提、动作和结果连成同一条证据链。对 Agent 完成的功能来说，这一点尤其重要，因为验收者通常不是实现者，不能把“我本地试过”当作可复查的事实。

一段有效的验收录屏，至少回答四个问题：

1. **验证的是哪套代码和环境？** 目标版本、客户端与远端拓扑必须能对应到被修复的问题。
2. **操作前是什么状态？** 如果缺少前置状态，最终画面可能来自预置数据、缓存，甚至另一套环境。
3. **执行了什么动作？** 从进入入口到触发查询的路径应当连续可见，避免只展示一个已经准备好的结果页。
4. **成功和未知分别如何呈现？** 不仅要看“想要的数据出现了”，还要检查错误、离线和未知值有没有被包装成成功或零值。

Issue #67 的前后录屏把这四件事压缩到了几秒内：同一条 `remote-only-record` 测试任务，修复前显示没有工作区和 Agent；修复后显示一个 archived 工作区、一条 Codex 会话，以及记录来源提示。这个对比让审查者不必相信实现者的叙述，可以直接检查产品声明是否成立。

这里还有一个很容易漏掉的细节：修复后的摘要写的是 `1 agents · wall unknown · tokens unknown`，不是 `0 tokens` 或 `$0`。零是一个已经测量过的数值，未知则表示没有足够证据。两者在成本统计、任务审计和后续自动决策中含义完全不同。**好的验收既确认新信息被找到了，也确认系统没有编造仍然未知的信息。**

## 自动化测试、日志与录屏各自证明什么

录屏不是自动化测试的替代品。它们回答的是不同问题：

| 证据 | 最擅长证明 | 单独使用时的盲区 |
| --- | --- | --- |
| 自动化测试 | 输入输出约束可重复，边界条件不会轻易回归 | 可能只测到 helper，没有证明生产入口真的接线 |
| 日志与持久化记录 | 请求是否发出、由谁响应、数据最终写到哪里 | 很难证明用户看到的语义和交互路径正确 |
| 验收录屏 | 指定版本和拓扑下，真实用户路径产生了预期结果 | 不易高频执行，也无法穷举所有边界条件 |

这三类证据组合起来，才形成完整闭环。自动化测试守住可重复的规则；日志解释跨进程、跨环境的数据路径；录屏验证这些部件在真实入口中确实组成了用户要的功能。

对 Issue #67 而言，自动化测试应覆盖环境候选选择、远端请求、记录合并和降级语义；运行证据应能确认客户端实际发出了 `taskRecords.get`；录屏则证明同一条远端独有记录最终在任务页被正确呈现。任何一层缺失，都可能留下“局部正确、整体不可用”的空档。

## 一份可复用的录屏验收清单

把录屏作为交付物时，不需要制作宣传视频。越短、越直接、越能对应验收声明，越有价值。我们可以沿用下面这份清单：

1. **先写一句可观察的验收声明。** 包含前提、动作、结果和关键的否定条件，例如“未知不得显示为 0”。
2. **固定版本与拓扑。** 记录 commit 或构建版本，并说明本机、远端、容器或配对环境分别承担什么角色。
3. **展示可辨认的初始状态。** 让任务、仓库、环境和必要的测试数据进入画面，但避免泄露 Token、邮箱等敏感信息。
4. **连续完成最短用户路径。** 尽量不剪辑；加载等待和短暂错误同样是产品行为，不应被藏起来。
5. **停留在关键结果上。** 给审查者足够时间读取状态、数量、时间与降级提示。
6. **同时保留反例和正例。** 对修复类任务，`before` 说明问题真实存在，`after` 证明同一路径发生了变化。
7. **保存原始文件和索引。** 用稳定文件名保存视频、前后截图和简短说明，让它们可以被 Issue、PR 或发布记录直接引用。

还应主动检查几种常见的“无效录屏”：只录最终画面、不交代测试拓扑；用本地数据代替原本出错的远端数据；剪掉加载和错误过程；没有关联到具体代码版本；只验证正常路径，却不检查离线、未知和权限不足时的语义。这些视频看起来像证据，实际仍要求审查者相信录制者的口头保证。

## 把“Agent 说完成了”改成可检查的交付

Agent 开发的效率越高，验收越不能停留在它自己的完成陈述上。实现者最熟悉代码，也最容易沿着自己预期的路径验证；独立审查需要的是一份不依赖这段上下文、可以暂停、重放和质疑的证据。

录屏的价值不在于“有视频”，而在于它迫使验收声明落到真实产品行为上：什么环境、什么入口、什么动作、什么结果，哪些值依然未知。对于 UI、桌面应用、跨环境路由和长链路 Agent 工作流，这往往是从“测试通过”走到“功能可用”最短的一步。

Issue #67 目前仍是公开的开放 Issue，本文也不把一次录屏写成发布状态声明。它展示的是一种验收方法：**代码与测试说明系统应该怎样工作，录屏证明目标版本在目标环境中确实这样工作。**
